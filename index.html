Section 01
The Problem

Every morning, software teams burn attention on coordination theatre instead of writing code.

Explore how Daybreak addresses it ↓

We observed three recurring frictions in daily engineering routines:

1. Manual status collection. Developers recite git logs and branch names already recorded in GitHub. Retyping updates by hand interrupts morning focus.

2. Delayed blocker visibility. Pull requests wait over thirty hours for reviews, and overnight test breakages go unnoticed until someone asks.

3. Repeated coordination. Engineers hesitate to nag peers directly, so stalled pull requests quietly accumulate delay.

Section 02
How it Works

A disciplined agent pipeline inside a shared team room.

Try the approval simulator below ↓
Scribe drafts, Sentinel recommends, Clerk acts only after human approval.
Evidence first: No link, no claim

If an engineer had zero activity in the repository over the last 24 hours, Scribe reports "No activity found." It never hallucinates or guesses unverified progress.

Our scope is deliberately compact: one repository, one chat room, and three agent roles. We do not attempt broad multi-repo tracker integration.

Scribe

Reads recent GitHub commits, PRs, and reviews. Drafts a clean three-line update per teammate with direct URLs.

Read-only · Never invents work

Sentinel

Evaluates room rules against repository status. Flags review delays, red CI, or stalled PRs and drafts polite nudges.

Read-only · Recommends only

Clerk

The sole role with GitHub write access. Posts review requests, issue comments, and labels only when a human lead explicitly approves.

Write-capable · Blocked without approval

Section 03
Why Switch

A static cron script with a webhook cannot coordinate multiple agents, persistent rules, and human gates.

Test the Friday rule toggle ↓

Daybreak relies on Switch because our workflow requires room coordination rather than a one-way notification pipe:

1. Agents in a shared room. Scribe, Sentinel, and Clerk share unified room context, exchanging intermediate proposals directly in conversation.

2. Rules changeable in chat. Team policies live in chat. Anyone can adjust rules (like quiet hours or Friday limits) without altering configuration files.

3. Context and decisions kept in the room. When an engineer approves a nudge or snoozes an alert, that decision is saved in room state to prevent repetitive noise.

Note: Verified chat client is Mattermost (bundled with Switch).

Section 04
Engineering Decisions

Deliberate architecture boundaries, safety guarantees, and deterministic test scenarios.

View verified setup commands ↓
Evidence first
Every statement drafted by Scribe links directly to a verifiable commit, pull request, or review timestamp. If zero repository events occurred for a developer in the past 24 hours, Scribe reports "No activity found" instead of hallucinating updates.
Permissions & least privilege
Scribe and Sentinel run with strictly read-only GitHub tokens. Only Clerk possesses write scope, gated behind human approval. Agents cannot merge pull requests or modify code.
Approval & idempotency
Proposed actions carry deterministic keys (e.g., nudge-pr42-2026-11-07). Clerk writes intent to a log and scans existing comments for hidden HTML markers, skipping duplicates automatically.
Blocker rules & thresholds
Sentinel checks four explicit baseline thresholds:
  • Review pending: review requested over 24 hours.
  • Red CI: failing check on an open PR older than 12 hours.
  • Approved unmerged: approved PR unmerged over 24 hours.
  • Stale ticket: assigned issue untouched for 3 days.
Setup and safety boundaries
Tokens pass via local environment variables. Dry-run mode (DAYBREAK_DRY_RUN=1) verifies logic without outbound GitHub API calls. All comments include attribution: [Daybreak, approved by @user].
